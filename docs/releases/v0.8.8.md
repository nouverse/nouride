**0.8.8 updates from 0.8.0 or later.** From 0.7.x, start 0.8.0 once first:
[Upgrading to 0.8](https://nouride.com/en/docs/deployment/upgrading-to-0-8/) has the way across.

No database migration. The event protocol is 1.6: a coding CLI's step may carry `like`, and `usage.basis` may be `cli`.

### Missions run by Claude Code or Codex keep to their limits

- **The token limit holds while a turn runs.** A coding CLI says what a prompt spent only when the prompt ends, and its
  mission can work for hours in a single turn: a mission with a 100M limit was past 107M before anything checked. Now
  Nouride reads what the CLI reports as it works, every few seconds, and stops the turn at the limit. The notice says
  the number is an estimate ("about 50.4M so far"), and the CLI's own count takes its place when the turn ends. On a
  live box, prompts that ended by themselves were counted exactly, and prompts stopped at the limit ended 2.6 to 6.1%
  past it.
- **The hours limit is checked while a turn runs too**, not only between turns.
- **Continue gives what the mission needs, and says what.** Continue used to set all three limits again from where the
  mission stood: after its token limit, a mission's 100 turns became 101 and its 8 hours became 8.96. Now it raises the
  limit that was reached, and any at 80% or more, by its setting, and leaves the others alone. The notice says what
  Continue gives: "100M more tokens", "8h more of work". Hours read `8h 58m`, never a decimal.
- **One warning at 80%.** It used to arrive in the same second as "reached its token limit".
- **Continue pressed while the stopped turn is still ending is kept** and runs after it. It was dropped, and the mission
  sat with no turn running.
- **Turns and tokens are shown as they are:** "2 turns · 215 steps" rather than a bar out of 100 turns, and tokens as
  unknown or "at least N" where the CLI has not said.

### The mission page

- **Turns as a timeline.** Each turn shows why it ran (it started, you answered, a job ended, on to the next step, a
  retry), with what that means on hover. Failures in a row fold into one line. The result is across the top, and the
  checklist, the questions and what counts as done are at the side. A mission waiting on you says what for at the top,
  with what Continue gives.
- **The list shows missions that ended in the last 3 days**, or the last 7, 14 or 30 days if you choose. Running and
  waiting missions are always listed. Before, it listed the 100 newest, however long ago they ended.
- **The page quotes the message that started the mission**, cut to one line. Its report and questions are in that
  message's language.
- **A mission started from a chat takes only that turn's work.** It used to take the chat's last task however old it
  was: a mission started for something new took the notes of work from three hours before, and left the chat pointing
  at the mission.
- A submodule checked out in a mission's worktree is no longer reported as kept for holding uncommitted work.

### English for the work, your language for you

- **One rule for every agent, Claude Code and Codex included.** Thinking, plans, notes, briefs to other agents, and the
  files and commits of the work are in English. Whatever reaches you is in your language: replies, the words between
  steps in a chat, a mission's report and questions, a document made for you. On one mission, 32 of 37 notes between
  steps had been written in the person's language, where nobody read them.
- **Working text that is not in English is sent back.** `plan`, `notes`, the task given with `ask_agent`, a helper's
  brief and a scheduled job's prompt are refused unless they are in English, and the agent writes them again.
  Commands, paths, code, quotes and names in other scripts do not count against it: `du -sh` is not French. Of about
  8,000 English texts it was measured on, none was refused.
- **A mission's goal is written whole.** Each turn starts from the goal, not from the conversation. A long goal points
  to a brief file, which has to be in English too.
- **A background job's result reaches you in your language**, whatever language its output is in. On 0.8.7 an agent
  asked by another left two commands running in the background. Their results went to the agent that asked, which
  reported them to your chat in English, and it read like a message from somewhere else. Now an agent asked by another
  does not move its commands to the background by itself, and a job it starts says its result goes to the agent that
  asked.

### Agents answered by Claude Code or Codex

- **`/status` says what answers the agent:** the CLI, its model, the context it last reported, and the tokens it spent.
  It used to print the pack's model and 0 tokens after hours of work.
- **Their tokens are recorded, at no cost and outside the daily spend caps.** The CLI runs on its own account, so spend
  alerts and the dashboard's spend leave its prompts out. A mission still counts them against its limit.
- **A change to SOUL.md reaches the CLI at its next turn.** A CLI reads its instructions when a session opens and keeps
  what it read, so a change saved on the Files tab waited until that session ended. Now a session opened on older
  instructions is closed at the next turn and a new one is opened. The CLI's own context starts over; Nouride keeps the
  conversation. `nouride agent reload <id>` does the same.
- **It can change its own CLI's model when you ask**, to one its CLI offers on the account in use, and tells you from
  what to what. Its pack's model, which answers Nouride's reviews and memory for it, is still set on the dashboard.
- **Signing a Claude Code account in from the dashboard works.** Claude Code waits for Enter in a way a newline does not
  give, so the code sat in the field and nothing came. The page now sends Enter as a terminal does, reads the screen as
  it is drawn, has an **Enter** button, and ends signed in or says why not.
- **It looks at its own missions, jobs and approvals with its `work` tool**, which its instructions now name. It used to
  try the `nouride` command, which cannot read the service's config as the agent's user. That command now says so in
  one line instead of a stack trace.

### An agent's persona changes only with an admin's yes

- An agent's SOUL.md, IDENTITY.md and AGENTS.md hold its boundaries and how it confirms things, and the agent could
  change them with `write` and `edit` without asking anyone. Now it proposes a change with the `persona` tool, the
  whole file or one section, with a reason, and you see every changed line. Only an admin answers, in a DM too. It is
  never approved for good, not even under `/approvals trusted`.
- A change of more than 24 lines or 2,400 characters is refused, so the agent proposes one section at a time. An edit
  made to the file after the question was shown is not written over.
- Another agent cannot answer the question through its `nouride` tool.
- MEMORY.md is still the agent's to write, and the Files tab works as before.
- Where agents run as the daemon's own user, a shell command can still write these files.

### Dashboard

- **Every diff is drawn the same way:** a skill draft against the skill on disk, an approval's change to a file or a
  persona. Long lines wrap, each changed line is tinted whole, and unchanged lines away from a change fold away. A skill
  draft's lines used to run past their box, cut on the left.
- **Saving on the Files tab disables Save at once.** The editor kept the old text as its base, and a second save failed
  with a conflict.

### Fixed

- After you applied skill drafts that merge skills, every reload logged that a coding CLI could not read the skill
  merged away, and that `skills.toml` names skills that do not exist. A skill gone since its agent loaded is now taken
  out of the CLI's folder without a warning. A switch for an archived skill is kept quietly, so it still holds if the
  skill comes back; a misspelt name still warns.
- "Agents ready as their own users" is logged once per agent, not again on every reload. Three skill drafts applied in
  a row wrote 21 of those lines.
- A coding CLI's steps no longer log "tool.like is not in the contract".
