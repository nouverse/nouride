### The daemon

- **However heavy a command an agent runs, the daemon keeps answering.** Everything an agent started ran in the daemon's own cgroup, under one soft memory ceiling: on a 2 GB box an audit's typecheck and test suite held the whole service over it for three quarters of an hour, and the kernel slowed the daemon with them until nothing answered — no crash, no restart, just silence on every chat. Now the daemon splits its cgroup when it starts: itself, with its memory protected and first call on the CPU, and every command an agent runs — `exec`, background jobs, terminal sessions, MCP servers — sharing a cap below the ceiling. The command that outgrows the cap is the one the kernel stops (`Killed`, exit 137), alone — and the agent is told, even when the exit code says otherwise: in `head | tail | wc -c` a killed `tail` leaves `wc` to exit 0. `nouride doctor` says how much they may hold together. **It needs the new service unit** (`Delegate=yes`): re-run the install script once — it leaves `.nouride/` alone; until then doctor warns. A Box rewrites its own unit once the update confirms, and splits from its next start. In Docker there is no unit to split: give the container a memory limit, and the commands are still what the kernel stops first.

### Agents

- **Asking another agent no longer holds the conversation up.** An agent that asks another with `ask_agent` still waits up to a minute for the answer. If the other agent is still working after that — a deploy, an audit — the agent you are talking to says it is on it, and you can keep talking. The answer arrives by itself when it is ready, saying what it answers and when it was asked. An agent that knows the work is long asks with `background: true` and does not wait at all.

- **That work is a background job, like a helper's.** It shows in `nouride jobs` as `ask nox: …` and on the dashboard. `/stop` in that chat or `nouride jobs kill <id>` stops it, and `job_max_ms` bounds it. It counts toward the same `[delegate] max_background` as helpers; when that is full, an ask simply waits as before and says why it took longer. A failure, the time limit, a stop or a restart is reported too, and an approval the other agent needs meanwhile still comes to your chat, saying whose work it is.

### MCP

- **MCP servers are installed once and switched on per agent, as skills are.** **Configure → MCP** is the install's list of servers, with **Explore** beside it: a server is added there once, with one credential or one login, and each agent's chip switches it on or off — two agents sharing Notion log in once. An agent's **MCP** tab only switches the install's servers on or off for it, and can give it a credential of its own (its own token, variables or login) where it should not use the shared one; a server marked **per agent** never shares one. Nothing to do when you update: each agent's `[[mcp_servers]]` moves into the list at the first start, switched on for that agent with the credential it had — logged in still — and the block leaves its `config.toml`; two agents with the same server become one entry, and the same name for different servers keeps both (`<name>-<agent>`, said in the log). The files: `agents/mcp.toml` holds the servers (`[[servers]]`, the same keys as before), `agents/<id>/mcp.toml` an agent's switches. From a shell: `nouride mcp add … [--agent <id>]`, `nouride mcp enable|disable <name> --agent <id>`, `nouride mcp rm <name>`. A server's tools go into every request of each agent it is on for — Notion's 65 are about 250 KB of definitions, which `nouride doctor` flags — so switch a large one on only where it is used.

- **Find MCP servers without leaving Nouride.** Configure → MCP has an **Explore** search over Nouverse's MCP catalog — a mirror of the official MCP registry, some forty-five thousand servers, ranked by Nouverse, so nothing of it is copied to your machine — showing Nouverse's picks before you type, and for each server who published it, how it would run on your machine (a remote endpoint, or a package through npx, uvx or docker) and what it asks for. One your machine cannot run says why — **needs uv**, **needs Node.js or Docker**, **Docker not usable** when it is installed but its daemon is not running or the service user cannot reach it — and how to get it on that machine: through `nouride pkg` on a native install, and in Docker the way that works there (uv an agent can put in the volume itself; Node.js is added when the image is built). **Add** opens the server form filled in with the version pinned, and won't save until the things only you can give — a token, a `{slug}` in the URL — are filled. From a shell: `nouride mcp search [words]` and `nouride mcp add --from <name> [--agent <id>]`. An agent can look too, with `mcp_search`, and answers with the link that opens Explore on the server it found: adding one is still yours to do. A search sends its words to `service.nouverse.tech`; `NOURIDE_MCP_CATALOG_URL` points elsewhere, or, set empty, turns the search off.

- **Log in to MCP servers that ask for it — Notion, Linear and the like.** A server from Explore whose registry entry lists no key says so on the form — no empty key box to wonder about. Added, one that answers asking for a login shows as **needs login**. **Connect** on its card opens its login page, and once you allow access it connects, its tokens kept in the secret store and renewed by themselves. From a shell, `nouride mcp login --server <name>` (or with `--agent <id>` for an agent's own login) prints where to log in and takes the address the browser lands on, so it works over SSH. A login the server stops taking is said once through your alerts, and an agent calling its tools is told a person has to log in again; `nouride mcp logout`, or Log out on the card, deletes the tokens. The card says who connected it, from where and when (`Connected — by <dashboard user> from the dashboard, …`) — never the account inside the service, which Nouride does not know.

- **A stdio MCP server's token stays out of `config.toml`.** `env_secrets = { GITHUB_TOKEN = "github_token" }` hands the server the secret named there, read from the secret store when it starts; a secret that is not set stops the start and says which variable. The server form has a row per secret variable and stores what you type; `nouride mcp add --env-secret GITHUB_TOKEN=github_token` names one you set with `nouride secret set <name> --stdin`. A token pasted as a value there is refused at load, as it is everywhere else.

### Dashboard

- **Lists scroll inside their card, and the tabs stay put.** Schedule, Webhooks, Agents, Models, People, Users, MCP and Skills fill the window; a long list scrolls in its own card instead of carrying the page — and its tabs — off the screen.

- **Tabs where a list has states.** Webhooks: All · Active · Paused · Failing, as Schedule has. Agents: All · Active · Idle · Paused · Unavailable. Models: All · OpenAI wire · Anthropic wire. Each with its count, in the same tab bar as every other page.

- **Skills: Live · Pending · Explore.** The All tab is gone — with nothing pending it showed exactly what Live did, so switching between them looked like nothing happened. The page opens on Pending when something waits on you. Explore opens on ClawHub's most downloaded skills instead of an empty box (kept an hour, so it costs ClawHub one request an hour at most), and searches only when you press Search, as MCP's Explore does now too.

- **The orchestrator is first, with its crown, wherever agents are listed** — the Agents list, MCP's and Skills' agent chips, Memory's Agent notes, Integrations, and the agent pickers in forms, which now start on it.

- **Something on its way shows.** The agent chip being switched spins, as do an agent's MCP switch, both Explore lists and Add, and the Pending list while it loads.

- An agent's **External tools** tab is called **MCP**, and Integrations has an icon of its own rather than MCP's plug.
