### Conversations, and what a turn writes

- **A turn writes the messages it added, not the whole conversation again.** A conversation was one JSON document, and every turn rewrote it: on a 300 KB conversation, some seventy pages through the database's log for the few kilobytes a turn adds — most of what a turn wrote to a Box's SD card. Each message is a row of its own now. Measured: one turn on a 300 KB conversation puts 24,752 bytes in the log, where it put 337,872. When a conversation reaches its cap, its oldest turn's rows go and the rest stay; a compaction writes the conversation once, as every turn used to.
- **The first start moves every conversation into the new table** (migration 055) and converts every vector (056), after a snapshot of the database. A conversation's first turn after it writes its messages once more; from then on, only what changed. The previous release refuses the new database and says how back: `nouride db restore` of the snapshot.

### Memory

- **A search by meaning reads only what it shows.** It read up to 5,000 conversations whole, and decoded each one's vector, just to rank them. It now ranks their ids against vectors held in memory and reads whole only the few near the top: at 50,000 items, 232 conversations where it read 5,203, in about a quarter of the time. The first search after a start reads the vectors into memory once — 30 MB for 50,000 items of 512 dimensions, 6 MB for 10,000.
- **Vectors are stored as bytes, and the upgrade converts every one already there** (migration 056): nothing is embedded again, and nothing costs a call.
- **Changing the embedding model no longer leaves search blind by meaning.** The old model's vectors are kept beside the new one's while it catches up — 2,000 items a night, or at once with Embed now — and searches are ranked by the old model until then, its query sent to the old model's provider while that profile still works. Once the new model has every item, the old vectors are deleted. Conversations filed since the change are found by their words until then. The dashboard says which model is ranking.
- **The nightly pass says when it falls behind, and what to set.** When an agent has more conversations a day than the pass files a night (`pass_per_night`, still 20 by default), the Memory page, `nouride memory`, `nouride doctor` and the log say so, with each agent's pace over the last week and the number per night that would clear what is waiting within a week.
- **A night can have a token budget: `[memory] pass_max_tokens`**, off by default. Past it, the pass stops before its next conversation and the rest wait for the next night. Each night's report says how many tokens it used — an estimate, and said to be one, when the provider reported none. `[llm.limits]` still applies.

### The CLI

- **A fresh install's CLI finds its install from anywhere**, before the setup wizard has written a config. It looked for the daemon under the directory it was run from — `nouride status` as root from its home said the daemon was another install's, and `nouride users reset` would have reset an empty database under the home directory.

### Upgrading

- **Docker:** `docker compose pull && docker compose up -d` — the production compose file follows `:0.7`. Check the configuration with the new image first: `docker run --rm -v ./.nouride:/app/.nouride ghcr.io/nouverse/nouride:0.7.12 nouride config check`.
- **Binary:** `nouride update --start`.
- **The way back** is the snapshot the first start takes before migrating: with the previous version's binary or image, `nouride db restore` names it. What was said after the upgrade is not in it.
