**0.8.9 updates from 0.8.0 or later.** From 0.7.x, start 0.8.0 once first:
[Upgrading to 0.8](https://nouride.com/en/docs/deployment/upgrading-to-0-8/) has the way across.

One database migration, `071`: an approval keeps the kind of question it was asked as, so who may answer it is read
from the question itself. 0.8.9 keeps a snapshot of the database before it migrates, named `…-before-071.db`. 0.8.8
refuses a database 0.8.9 has migrated and says so; to go back, `nouride db restore` that snapshot first. The event
protocol is unchanged, 1.6.

On Docker, check your configuration with the new image before you switch:
`docker run --rm -v ./nouride:/app/.nouride ghcr.io/nouverse/nouride:0.8.9 nouride config check`, with the volume your
compose file mounts.

### Only an admin can make someone an admin

0.8.8 made a change to an agent's persona an admin's alone to answer. Who is an admin comes from People: a chat counts
as an admin's when the person holding that chat id in People holds an admin's dashboard account. An agent at
`trusted` could change that without asking anyone. It could link a chat to the admin's entry with
`nouride access approve <code> --as <person>`, and that chat then answered persona changes and every other question
only an admin may answer.

- **A change to who People says a person is always asks now, `trusted` included**, and only an admin answers it:
  `nouride access approve <code> --as <person>`, `--me` or `--new <name>`, `nouride people set` and
  `nouride people remove`, run by an agent. A chat that is not an admin's and answers it is told "Only an admin can
  answer this one: it changes who People says a person is, and an admin is one.", and the question stays open.
- **A program installed for every agent** (`nouride tools run`) is an admin's to answer too: it installs as the
  daemon's user, which can change People.
- An admin answers in a chat, a one-to-one included, or on the dashboard. An operator's dashboard account cannot answer
  it, and another agent cannot answer it through its `nouride` tool.
- **An operator's dashboard account can no longer send a message as somebody else.** It could send `/approve` as the
  admin through the command line's way in and answer an admin's question with it.
- A question asked before the upgrade and still waiting keeps the rule: the migration marks a waiting persona change,
  change to People or program for every agent as an admin's.
- The rest of `nouride access` — approving a code on its own, `allow`, `deny`, `block`, `revoke`, `reset`,
  `unblock` — asks as before: it changes who may talk to the agents, not who is an admin.
- The Trusted card on the dashboard and `nouride config explain` list what `trusted` still asks.
- **Where agents run as the daemon's own user** (Docker, a Mac, an install without the helper), a shell command can
  still write `[[people]]` in `config.toml`. There, "only an admin answers" holds only where everyone who can chat with
  the agents is an admin; the manual says so.

### Coding-CLI accounts in the audit log

Adding, removing and signing in a coding-CLI account is written to the audit log, with who did it and never the token.
On 0.8.8 an account could go from the Coding CLIs list with nothing saying who or what removed it.

### Agents answered by Claude Code or Codex

- **They get the skills of the projects in their `skill_roots`.** A coding CLI works in its own folder, not the
  repository, and only the agent's own skills were copied into its skills folder: a pack that named a repository in
  `[workspace] skill_roots` gave the CLI nothing from that repository's `.agents/skills`. They are copied with the
  agent's own now, again before each turn, so a skill added to the repository reaches the CLI at its next message. A
  project skill named like one of the agent's own is left out, as it is from any agent's prompt.
