**0.8.18 updates from 0.8.0 or later.** From 0.7.x, start 0.8.0 once first:
[Upgrading to 0.8](https://nouride.com/en/docs/deployment/upgrading-to-0-8/) has the way across.

On Docker, check your configuration with the new image before you switch:
`docker run --rm -v ./nouride:/app/.nouride ghcr.io/nouverse/nouride:0.8.18 nouride config check`, with the volume your
compose file mounts.

### Updates

- **Choose which releases this install is offered: the newest, or a long-term line.** On the dashboard's Update page,
  or `nouride update --track latest|lts`. `latest` takes every release as it comes; `lts` moves to a long-term line,
  1.0 the first, and stays on it, taking its fixes only. Both say what the other would install, and until a newer line
  is out beside 1.0 they offer the same.
- **Every release on the channel is read, and the newest is the highest version,** not the latest published. An older
  install whose way forward was past the first page of releases, or a fix to an older line published after a newer
  release, was offered the wrong one or none.

### People

- **Each person is a file of their own, `people/<key>.toml`,** beside `config.toml`, the file's name their key. People
  were a list inside `config.toml`, so every change to anyone's notes or accounts rewrote the file that runs the
  daemon and pushed out its backups: on a busy box all five were from the same minute. Each person's file now keeps
  its own last versions.
- **A file edited by hand stays edited.** The next change from People or an agent patches the file as it is on disk;
  it used to put back what the daemon had read at its start. A file that does not load is named in the log and that
  person left out until it does; the daemon starts.
- **The first start moves everyone by itself.** Each person is written to their file, and the list in `config.toml`
  is kept, marked as moved, so going back to 0.8.17 finds the people it had, and what 0.8.17 changes there comes
  along when 0.8.18 starts again.

### Backups

- **A burst of saves no longer pushes out yesterday's config.** A file's newest backup is still the version just
  before the last save, but the older ones move along at most once an hour, so a morning of People and Memory changes
  keeps what the file said the day before. What falls off the last backup goes to a `history/` folder beside the file,
  twenty versions deep, and a file the first start of a new version rewrites is kept once as `<file>.before-<version>`.
- **The snapshots hold what they missed:** `config.toml`, the people, the install's MCP servers and the skill pool,
  each in its own folder under `data/backups/` on the same weekly schedule, and each agent's skill and MCP switches
  with its pack. An approved improvement to a skill keeps the version it replaced.
- **Your secrets can go into the snapshots, sealed to a passphrase only you hold.** `nouride secret seal --stdin`
  sets it, and from then on each config snapshot holds the secret store sealed: the box can write it and cannot read
  it, so a lost backup drive gives nothing away. `nouride secret unseal` opens one with the passphrase on a rebuilt box.
  Without a passphrase nothing changes, and `nouride secret` says the snapshots do not hold your secrets.
- **What Nouride keeps for itself is in its database now, so a snapshot brings it back:** which agents are asleep,
  when each alert was last sent, each external agent's CLI sessions and the accounts added on the Models page, what the
  last start advised. They were separate files beside the database that no snapshot took, so `nouride db restore` put
  back the conversations and left these as they were. The first start moves them in by itself and leaves the old files
  where they are, so going back to 0.8.17 still finds them.

### Reliability

- **A chat's `/model` and `/effort` stay after a restart,** and so after an update: every restart used to put the chat
  back on the agent's own model and level. `/model default`, `/effort default`, `/reset` and a rollover still drop
  them, and `/new` keeps them, as before.
- **An approval still waiting when the daemon crashed or lost power keeps who asked and what `/approve always` would
  remember,** as it already did across a clean restart. Before, after a crash a question asked in a group could be
  answered only by an admin, and it came back without **Always**.
- **A command run while the daemon was starting or tidying its database no longer says the database is broken.** It
  waited for nothing, and `nouride doctor`, `db verify` or `gateway rename` could answer that the file was unreadable
  and should be moved aside. It now waits, as the daemon does, and a database held for longer than five seconds is
  called busy.

### Moving an install

- **An install moved or copied to another folder keeps working there.** Its first start in the new folder finds every
  path the database kept under the old one and names it under the new: attachments in past conversations open, job
  logs are found, a mission goes on in its folder, a scheduled command runs where it did, and an "always allow" given
  for a folder still holds (one given for a command that is handed a secret asks once more). Before, a copy started
  elsewhere looked for all of these where the old install was. A `data_dir` or `workspace_dir` moved to another disk
  on its own is followed the same way, and what stayed keeps its paths. This works for an install that has started on
  0.8.18 at least once where it was.
