### A CLI that scripts and agents can read

- **Exit codes that mean something.** `0` done, `1` failed, `2` asked wrongly. An unknown action — `nouride jobs lst` — used to fall through to the listing and exit 0, and a missing argument printed its usage and exited 0 too, so a script could not tell a typo from a success.
- **`--json` on every command**: one object on stdout, `{"ok", "data", "error", "hint"}`, where `data` is what the lines were printed from. An agent no longer has to read a table back out of terminal formatting.
- **`--flag=value`, and `--`.** Both spellings of a value work everywhere, and nothing after a bare `--` is read as a flag: `nouride policy check -- ls --help` asks about `ls --help` rather than showing help.
- **One way to pipe a secret in: `--stdin`.** `secret set`, `provider add`, `gateway add` and `mcp add` each had a name of its own; the old ones still work.
- **`nouride restart --wait` and `nouride update --start --wait`** return once the daemon is back, saying each step of the restart as it happens, and exit 1 if it does not come back — or comes back on the version it was meant to leave.
- **`nouride doctor` reads what the daemon and the disk already know:** free space against the threshold the daemon logs at, the database's own integrity check, what `/health` counts as an issue, and the modes of the token, secrets and database. `--fix` narrows a mode that is more open than the daemon makes it.
- **The hint when the daemon is down names the way it runs here** — `systemctl` for the service the installer set up, `launchctl`, `docker compose` — instead of always suggesting `nouride start`, which on a service box started a second, unsupervised copy.
- **`nouride help`** lists the commands that work without a running daemon on their own.

### Chat platforms and providers

- **A long answer no longer runs into Telegram's limit.** Each part waited for nothing, so a twelve-part reply went out faster than Telegram's message-a-second for a chat, and the 429 that came back was retried at once and then resent as plain text, into the same limit. Every part now waits its turn — a second apart in a chat, three seconds apart in a group — and a 429 is waited out for as long as Telegram asks. Discord gets the same, at five messages in five seconds a channel. The progress line is not held behind the answer.
- **A refused bot token is said at once.** A wrong or revoked token was reconnected to ten times over ten minutes, then reported as a dropped connection. Telegram and Discord now say when it is the token, the gateway stops after one more try, and the alert says the token was refused and what to do.
- **Nougate says who answered.** From Nougate 1.1.0, every response names the provider that served it, the model, and how many providers it tried. Nouride keeps them with each model call, and `nouride turns show` prints `via <provider>` beside it — the calls can be split by what actually ran, not only by what was asked.
- **`identify = true` on a provider profile** sends which agent and conversation each request is for — `user`, `prompt_cache_key` and an `x-client-id` header to an OpenAI-compatible endpoint, `metadata.user_id` to an Anthropic one — so a gateway such as Nougate can tell six agents apart, and a conversation's requests reach the cache its prompt is already in. Off unless set: a strict server rejects fields it does not know.

### Agents working together

- **Helpers and the agents an agent asks count toward `max_concurrent_turns`.** `delegate` ran four helpers and `ask_agent` a peer per call, none of them counted, so eight conversations each delegating four meant forty provider streams with the ceiling reading eight. They now run on the asking turn's own slot — it is waiting on them, not calling the provider — and take more only where the ceiling has room. On a busy daemon they run one after another, and none fails for want of a slot.
- **An agent asked with `ask_agent` is at work in that chat until it answers.** Someone addressing it there is told it is busy instead of starting a second turn of the same agent beside the first, a scheduled turn or a job's result waits for it, and asking it again there is refused with a reason the asking agent can act on.

### Secrets that stay with the commands that need them

- **`[security.exec_secrets]` binds each secret to its commands**: `pypi_token = ["twine upload"]`. Every command an agent ran held every secret it had, so one instruction planted in a page it read could send them anywhere with `curl`. A bound secret reaches only a command that starts with one of its commands — every part of a command line, so `twine upload && curl …` gets nothing — and that command asks before it runs at every approval level but `none`, naming the variables. *Allow always* remembers the secrets and the script the command runs, so editing either asks again. The prompt tells the agent which commands get which secret.
- **Nothing changes until you bind one.** `["*"]`, and the old list form, still hand a secret to every command without asking, and the daemon names each such secret when it starts so you can scope it.

### One stream of what turns do

- **`nouride events`**: a turn starting and ending, each step, the answer as it grows, each tool call and each model call, as one stream with one cursor. A page, or `-f` to follow it, which picks up where it was if the connection drops. The same stream is `GET /api/control/events/stream` for anything that wants to watch a turn as it runs — it is what the 0.8 editor integration is built on.
- **A tool call to an MCP server is written down**, like every built-in tool's: who ran it, with which arguments, in which turn. They went unrecorded, so an issue opened on GitHub through a server left no trace of who asked for it. They now also reach the turn's event stream.
- **The dashboard follows it.** An open conversation asked the daemon what changed every half second while a turn ran; it now hears the moment something is written, and checks in every two seconds only as a safety net.

### Updates you can take back

- **`nouride update --rollback`** puts the previous version back when the new one starts but is wrong — something the update guard, which only catches a version that does not start, cannot see. It says first which build it would put back and whether the database goes back with it: only when the update migrated it, to the snapshot that migration took, with the time from which work is lost. `--apply` does it with the daemon stopped, the database first so a bad snapshot changes nothing, and the database it replaces is kept. The version you left is not taken again automatically, and the same command goes forward again.
- **`install.sh` keeps the build it replaces** in `.nouride-previous/`, as `nouride update` does, so the way back exists after either kind of upgrade — and a rollback refuses a kept build some other version put there.
- **A new version has to prove itself before it is kept.** Off a box it confirmed itself at the first look, fifteen seconds into a boot it might not survive. Now it needs a chat gateway connected and a message handled, or five minutes up with nothing to handle; until then the guard can still put the old one back.
- **Public releases are signed.** Each public checksum file now has a signature beside it, and an update verifies it where the release carries one — the private editions always did. Releases before 0.7.4 install as they did.

### Upgrading

- **Docker:** `docker compose pull && docker compose up -d`
- **Binary:** `nouride update --start`

No configuration changes are needed. The first start migrates the database to schema 51 (the event stream, and who answered each model call), taking a snapshot first; `nouride update --rollback` puts that snapshot back with 0.7.3 if you need to go back. To scope a secret, see `[security.exec_secrets]` — until you do, secrets reach every command as before, and the daemon names each one when it starts.
