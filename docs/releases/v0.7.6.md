### One stream, with a contract

- **The event stream is now a contract, version 1.0.** What every kind of row carries is written down once — `docs/EVENTS.md` has it, with what a reader can rely on and how the stream may change: within 1.x only by adding a kind or an optional key. `GET /api/control/events` answers `version`, and both routes send `x-event-protocol: 1.0`. Anything that reads the stream — the dashboard, `nouride events`, the editor integration 0.8 builds on it — can count on a row keeping its shape from here on.
- **A retry and a compaction are rows of their own.** When a provider refuses or fails and the request is asked again, a `retry` row says so before the wait — the kind of failure, which attempt, how long until it — instead of the turn going quiet. Making the conversation fit is a `compact` row: started, done or failed, and when older messages or tool results were left out to make room. Both show in `nouride events`, `nouride turns show` and the dashboard's step log.
- **A tool call's rows pair by `callId`.** Its start, its audit row and its end carry the same id, unique within the turn — a provider that numbers every round's calls from `call_0` no longer makes two calls look like one. The audit row and the end are written together, so a reader never sees one without the other.
- **A tool call costs three writes to the database, where 0.7.5 made seven** — measured: the start, the journal's note that it began, and its result in one transaction. A turn's steps live only in the event stream now; steps of turns recorded before 0.7.4 are still read from where they were.
- **A row is announced only once it is committed**, and one rolled back is never announced.
- **A model call's usage row says which conversation it belongs to**, as the rest of a turn's rows do, so a reader following one chat sees what it cost.

### Background jobs

- **`[security] job_max_ms` stops a background job that runs too long.** Off unless you set it. Set, a job still running after that many milliseconds is stopped the way `nouride jobs kill` stops one, and its agent is told it ran out of time and did not finish — not that it failed — while the daemon posts that line in the chat itself. The agent is told the limit when it starts a job. A service — a dev server, a tunnel — is exempt. A stopped job whose output a detached process it started kept open is no longer held as running forever.
- **`on_complete` works for every agent.** An agent using the shared `exec` — most of them — was told its instruction would run when the job finished, and it never did.

### CLI

- **`--json` answers with what a command found, even when no daemon is running.** `nouride db`, `config`, `policy`, `gateway rename` and `pkg` answered `data: null` — `nouride config schema --json` printed no schema — and what a command's own work logged reached stdout ahead of the answer, so `nouride db backup --json` began with a log line. A command now logs to stderr, at warn unless `LOG_LEVEL` says otherwise, and the two usage errors of `nouride config` that exited 0 and 1 exit 2.

### Restarts and updates

- **An open dashboard conversation no longer slows a restart to thirty seconds.** A followed event stream never ends on its own, and the daemon waited for it until its shutdown deadline, then forced an exit that skipped closing the database cleanly. The stream is now ended first and the reader reconnects to the new daemon where it left off — `nouride events -f` included.

### Upgrading

- **Docker:** `docker compose pull && docker compose up -d`
- **Binary:** `nouride update --start`

No database changes. One new optional key, `[security] job_max_ms`, off (`0`) by default.
